# Stage 4: 反馈循环

## 目标
每个 sprint 结束时自我评估 + 外部评估，形成闭环。

## 评估维度与硬阈值

| 维度 | 满分 | 硬阈值 | 说明 |
|------|------|--------|------|
| 产品深度 | 10 | ≥ 7 | 功能是否完整、有深度，还是只有空壳 |
| 功能性 | 10 | ≥ 7 | 是否能正常工作，有无明显 bug |
| 视觉设计 | 10 | ≥ 7 | 是否有独特设计、一致视觉语言，还是模板堆砌 |
| 代码质量 | 10 | ≥ 7 | 代码结构、命名、错误处理、测试覆盖 |

## 前端设计评估细则（4 个子维度）

1. **设计质量**：整体感 vs 部件堆砌？色彩、排版、布局、图像是否创造独特氛围
2. **原创性**：是否有自定义决策，还是模板/库默认/AI 生成模式
3. **工艺**：技术执行 — 排版层次、间距一致性、色彩和谐、对比度
4. **功能性**：用户能否理解界面、找到主要操作、完成任务

## 评估流程

```
1. Evaluator 使用 Playwright MCP 操作运行中的应用
2. 逐维度评分 (0-10)
3. 任何维度 < 7 → sprint 失败
4. 失败时: 写详细反馈到 docs/exec-plans/feedback-[sprint-id].md
5. Generator 读反馈，在下一个 sprint 修复
6. 全部 ≥ 7 → sprint 通过，标记 feature passes: true
```

## 反馈格式

```markdown
# Sprint [ID] 评估报告

## 评估日期: [日期]
## 评估特性: [F001 - 用户注册]

## 评分

| 维度 | 得分 | 通过 |
|------|------|------|
| 产品深度 | 8/10 | ✅ |
| 功能性 | 5/10 | ❌ |
| 视觉设计 | 7/10 | ✅ |
| 代码质量 | 6/10 | ❌ |

## 详细反馈

### 功能性 (5/10)
- 注册成功后未返回 201 状态码，返回了 200
- 密码强度校验缺失
- 重复邮箱注册返回 500 而非 409

### 代码质量 (6/10)
- UserService.Register 方法 87 行，超过 50 行限制
- 缺少单元测试
- 异常处理使用 catch-all，不符合规范

## 修复建议
1. 修改注册成功返回码为 201
2. 添加密码强度校验逻辑
3. 重复邮箱返回 409 Conflict
4. 拆分 Register 方法为 3 个子方法
5. 添加 UserService 单元测试
6. 使用具体异常类型替代 catch-all
```

## 关键原则

- **硬阈值不留情面**：低于 7 就是失败，没有"差不多"
- **反馈必须具体**：指出具体问题 + 给出修复建议
- **闭环**：反馈 → 修复 → 重新评估 → 通过
- **Evaluator 是用户代理**：像真实用户一样点击操作
